## 0. 目的与不可破的红线

### 0.1 什么叫「变砖」

**需要拆机、接调试器（SWD/JTAG）才能恢复** 的状态才算变砖。
只是「APP 跑不起来、需要重新升级」不算 —— 那是可用性下降，不是变砖。

### 0.2 本 Bootloader 的五条红线

任何测试、任何时刻，都不得越过这五条：

| # | 红线 | 由什么保证 |
|---|---|---|
| R1 | Bootloader 自身永不被升级流程覆盖 | Flash 驱动拒绝擦除 Bootloader 区；分区不重叠（编译期自检） |
| R2 | 任何时刻断电，重启后都能重新进入 IAP | 原子提交顺序：先置 DOWNLOAD 再擦 APP |
| R3 | APP 区损坏 / 非法时，绝不跳转进去 | 向量表校验 + 可选整镜像 CRC32 |
| R4 | APP 跑不起来时，系统能自己退回来 | 看门狗自确认 + 自动回滚 |
| R5 | 任何情况下都存在人工救援通道 | Backdoor 强制进 IAP |

**测试的全部工作，就是逐条尝试「怎么把这五条弄坏」。**

### 0.3 判定通过的标准

| 结果 | 含义 |
|---|---|
| **PASS** | 断电/异常后重启，设备仍能进入 IAP 或被正常跳转，串口有明确日志 |
| **DEGRADED** | 能恢复，但需要人工干预（按一下复位键 / 用 Backdoor）—— 可接受，记录在案 |
| **FAIL** | 需要接调试器才能恢复，或数据被破坏（如 Bootloader 被擦）—— 不可接受 |
| **BRICK** | 调试器也救不回来（例如全片擦除后没留备份）—— 严重事故 |

## 1. 测试环境与工具

### 1.1 硬件

| 项 | 值 |
|---|---|
| 目标芯片 | STM32F401RET6（512KB Flash / 96KB SRAM，S0-S7） |
| 调试器 | DAPLink（CMSIS-DAP，`0d28:0204`） |
| 串口 | CH340 → COM3，115200 8N1 |
| 供电 | USB 供电（**暴力测试需改为可控电源**，见 §4） |
| 注意 | **SWD 走线不宜过长** —— 实测线长会导致 `ACK '6'` 等非法响应，接线过长的现象会被误判成探针固件缺陷 |

### 1.2 工具

```
TestApp/tools/board_test.py       板端测试驱动（烧写/进IAP/升级/观察）
TestApp/tools/ymodem_send.py      YMODEM-1K 上位机
TestApp/build_app.py              构建 APP（支持 --fail N 注入故障）
Bootloader/tools/build.py         构建 Bootloader（命令行量 ROM）
```

常用命令：

```bash
# 完整链路：烧 Bootloader → Backdoor 进 IAP → 升级 → 无缝观察
python TestApp/tools/board_test.py run \
    --bootloader MDK-ARM/LUMOS-bootloader/LUMOS-bootloader.hex \
    --app build/app_fail1.bin --observe-s 45

# 只观察（不碰目标）
python TestApp/tools/board_test.py observe 30
```

> ⚠️ **升级与观察必须复用同一个串口连接**。中间断开再重开会错过
> 「升级完成 → 复位 → 重新决策」那几百毫秒，而复位原因正是在那里打印的，
> 是最关键的证据。

### 1.3 测试固件集

| 文件 | 制造方式 | 用途 |
|---|---|---|
| `app_test.bin` | `build_app.py` | 正常固件：能跑、会喂狗 |
| `app_fail1.bin` | `build_app.py --fail 1` | 不喂狗 → 验证看门狗自确认 + 回滚 |
| `app_fail2.bin` | `build_app.py --fail 2` | 启动即 HardFault → 验证崩溃路径 |
| 非法向量表固件 | 手工改 `app_test.bin` 的前 8 字节 | SP/PC 越界 → 验证向量表校验 |
| 截断固件 | `head -c 800 app_test.bin` | CRC 必错 → 验证校验拒绝 |
| 超长固件 | 填到 >368KB | 验证空间不足的处理 |

## 2. 失效模式清单（核心）

按「**怎么让它变砖**」组织，而不是按功能。每条都要有触发方法、预期行为、
判定依据，以及执行状态。

状态图例：`✅ 通过` / `❌ 失败` / `⚠️ 降级可用` / `⬜ 未测` / `🔄 回归中`

### A. 供电异常（最容易变砖的一类）

| ID | 场景 | 触发方式 | 预期行为 | 状态 |
|---|---|---|---|---|
| A1 | 擦除 APP 扇区过程中断电 | 继电器在擦除期间切断 | 重启后状态仍是 DOWNLOAD → 停在 IAP 可重刷 | ⬜ |
| A2 | 写入 APP 数据过程中断电 | 传输中途切断 | 同上；已写入部分不产生副作用 | ⬜ |
| A3 | 写配置区槽位中断电 | 状态迁移瞬间切断 | 该槽 CRC 错 → 被跳过，用上一个有效槽 | ⬜ |
| A4 | 配置区扇区擦除中断电 | 把槽位用满后触发擦除，期间切断 | 全 0xFF → 判为 INVALID → 停在 IAP 可重刷 | ⬜ |
| A5 | 升级完成、状态置位瞬间断电 | 精确卡点（难） | 要么旧状态要么新状态，无中间态 | ⬜ |
| A6 | 跳转瞬间断电 | 见 §4 的自动化方案 | 重启后走正常启动决策 | ⬜ |
| A7 | APP 正常运行中断电 | 随机时刻切断 | 下次上电正常启动，无副作用 | ⬜ |
| A8 | 反复快速断电（电压抖动） | 1 秒内多次通断 | 每次都能重新进入 IAP 或正常启动 | ⬜ |
| A9 | 欠压（BOR 临界） | 可调电源缓慢降压 | 表现为 POR/BOR 复位，不破坏数据 | ⬜ |
| A10 | 上电电压缓慢上升 | 可调电源缓升 | HSE 起不来时退回 HSI，串口仍可用 | ⬜ |

### B. 固件本身有问题（CRC 正确也算）

| ID | 场景 | 触发方式 | 预期行为 | 状态 |
|---|---|---|---|---|
| B1 | CRC 正确但一启动就 HardFault | `--fail 2` | 看门狗拉回 → 计数 → 3 次后回滚 | ⬜ |
| B2 | CRC 正确但不喂狗（卡死） | `--fail 1` | 同上 | **✅ 通过**（2026-10-04） |
| B3 | 向量表非法（SP/PC 越界） | 改 bin 前 8 字节 | 向量表校验拒绝 → 作废 → 停在 IAP | ⬜ |
| B4 | 固件超出 APP 区 | 用 >368KB 的文件 | 大小检查拒绝，不擦除不写入 | ⬜ |
| B5 | 固件为 0 字节 | 空文件 | 首包解析出 size=0 → 拒绝 | ⬜ |
| B6 | 固件为 0xFF（空片） | 全 0xFF 文件 | 向量表校验失败 → 作废 | ⬜ |
| B7 | 固件损坏（CRC 错） | `head -c 800` 截断 | 传输层 CRC16 或整镜像 CRC32 拦下 | ⬜ |
| B8 | 固件正常但运行中途死机 | 在 APP 里延迟后停喂狗 | 看门狗拉回 → 回滚 | ⬜ |

### C. 配置区异常

| ID | 场景 | 触发方式 | 预期行为 | 状态 |
|---|---|---|---|---|
| C1 | 配置区全 0xFF（首次上电） | 擦除 0x08060000-0x0807FFFF | 判为 INVALID → 进 IAP | **✅ 通过** |
| C2 | 配置区随机数据 | 用调试器写入随机值 | 槽 CRC 不匹配 → 跳过 → 视为无有效槽 | ⬜ |
| C3 | 最新槽 CRC 错，旧槽有效 | 改坏最新槽 | 回退到上一个有效槽 | ⬜ |
| C4 | 槽位用尽触发扇区擦除 | 连续状态变更 2048 次 | 擦除后从头写，状态延续 | ⬜ |
| C5 | 配置区被外部误写 | 随机写 | 同上；不导致跳转到坏固件 | ⬜ |
| C6 | 状态为 DOWNLOAD 时重启 | 传输中途复位 | 判为未完成 → 停在 IAP 可重刷 | **✅ 通过** |

### D. 协议 / 上位机异常

| ID | 场景 | 触发方式 | 预期行为 | 状态 |
|---|---|---|---|---|
| D1 | 传输中途 PC 断开 | 拔串口线 | 超时 → 回到等待 → 状态留在 DOWNLOAD，可重刷 | ⬜ |
| D2 | 数据帧 CRC 错 | 上位机故意算错 CRC | 板端回 NAK → 要求重传 | ⬜ |
| D3 | 序号错乱 / 重复 | 重发同一序号 | 按 YMODEM 语义处理，不写错位置 | ⬜ |
| D4 | 声明大小与实际不符 | 首包 size 写小/写大 | 写小：剩余数据被拒；写大：超时失败，状态不留 VALID | ⬜ |
| D5 | 文件名超长 / 非 ASCII | 80 字节文件名 | 截断处理，不越界 | ⬜ |
| D6 | EOT 后不发批次结束包 | 手工构造流程 | 数据已收全 → 仍判成功（结束帧非必需） | ⬜ |
| D7 | 传输被 CAN 取消 | 上位机发 CAN | 干净中止，状态回到可重刷 | ⬜ |
| D8 | 波特率不匹配 | 上位机用 9600 | 收不到握手 → 板端超时后重新等待，不误判 | ⬜ |
| D9 | 板子发 'C' 前上位机就发数据 | 主动抢发 | 数据被 flush_rx 丢弃 → 板端继续等握手 | ⬜ |
| D10 | 上位机发送过程中复位 | 硬件复位板子 | 状态回到 DOWNLOAD 判定，可重刷 | ⬜ |

### E. Bootloader 自身

| ID | 场景 | 触发方式 | 预期行为 | 状态 |
|---|---|---|---|---|
| E1 | APP 误写 Bootloader 区 | 把 bin 烧到 0x08000000 | 这是烧写工具行为，**不在 Bootloader 职责内**；但 IAP 流程必须拒绝擦 S0 | ⬜ |
| E2 | Bootloader 区内容损坏 | 调试器改几个字节 | 无法自愈（固件本身坏了）—— 需要重新烧写，属正常 | ⬜ |
| E3 | 分区配置写错（地址重叠） | 改 `bl_config.h` 制造重叠 | **编译期 `#error` 拦截** | **✅ 通过**（编译期自检） |
| E4 | 看门狗超时设置过短 | 设为 1 秒 | 擦除 128KB 扇区（最坏 4 秒）会被咬 → 必须在文档里明确下限 | ⬜ |
| E5 | HSE 起不来 | 拔掉晶振 / 短接 | 退回 HSI 16MHz，串口仍可用（日志会提示） | ⬜ |
| E6 | 串口引脚被外部拉死 | 强拉 TX/RX | 不影响启动决策（只影响日志） | ⬜ |

### F. 人为误操作

| ID | 场景 | 触发方式 | 预期行为 | 状态 |
|---|---|---|---|---|
| F1 | 用 ST-Link/OpenOCD 全片擦除 | `erase` 全片 | 不走 IAP 流程，无法防护 —— **要求保留完整备份** | ⬜ |
| F2 | 上电时串口有噪声（误触 Backdoor） | 上电瞬间狂发字符 | 只认 `0x7F`；其它字节被丢弃 | ⬜ |
| F3 | 上电时正好收到 `0x7F` | 刻意发送 | 进 IAP —— 这是设计行为 | **✅ 通过** |
| F4 | 把 APP 固件当 Bootloader 烧到 S0 | 手工指定地址 | 烧写工具行为；上电后会跑 APP 而非 Bootloader | ⬜ |

## 4. 断电测试的自动化

手动拔插电源无法精确卡点。两种可行方案：

### 方案一：USB 继电器（推荐，成本低）

```
USB 开关继电器（如 LCUS-1）
    ↓ 串口控制
PC 脚本：board_test.py 增加 --cut-at 参数
```

思路：让脚本在「串口后台上持续监听 + 到了目标时刻立刻切继电器」。
目标时刻按日志特征触发，例如：

| 目标时刻 | 触发条件（监听串口） |
|---|---|
| 擦除前 | 出现 `[session]` 首包日志后 50ms |
| 擦除中 | 首包 ACK 收到后 200ms（此刻正在擦） |
| 写入中 | 收到第 1 个数据包 ACK 后 10ms |
| 状态提交中 | 收到 EOT ACK 后 5ms |
| 跳转前 | 出现 `[boot] jumping to app` 后 1ms |

**这套脚本本身也是交付物之一**（`board_test.py` 预留了钩子）。

### 方案二：手动 + 高频记录

退而求其次：用「上位机在任意时刻 Ctrl-C + 立刻断电」制造随机断电点，
靠**次数**覆盖概率。做 50-100 次，记录每次重启后的日志。
虽然不精确，但足以暴露系统性问题。

## 6. 已完成的验证（截至 2026-10-04）

| 项 | 结论 | 证据 |
|---|---|---|
| 上电进 IAP、分区信息正确 | ✅ | 串口 banner + 分区地址 |
| YMODEM 传输 + 擦写 + CRC 校验 | ✅ | `[session] done: size=... crc=...` |
| 跳转到 APP、APP 稳定运行 | ✅ | 22 秒 22 个 tick，间隔恒为 1，无重启 |
| 看门狗自确认（APP 零侵入） | ✅ | 升级后按复位 → `clean boot -> firmware self-confirmed` → state=VALID |
| 自动回滚 | ✅ | 故障固件 3 次被看门狗拉回 → `rollback` → 停在 IAP |
| Backdoor 强制进 IAP | ✅ | 复位窗口内持续发 `0x7F` → `backdoor triggered` |
| 配置区全空的容错 | ✅ | `state=INVALID` → 进 IAP |
| 状态 DOWNLOAD 时重启 | ✅ | `state=DOWNLOAD` → 判为无可用固件 → 进 IAP |
| 编译期分区自检 | ✅ | 地址改动出错时 `#error` 拦截 |
| ROM 占用（16KB 硬约束） | ✅ | 15.1 KB，余量 1.2 KB |

### 本轮实测暴露并修复的问题（都是"只在真板上才现形"的）

| # | 问题 | 根因 | 影响 |
|---|---|---|---|
| 1 | 跳转后 APP 完全不输出 | `HAL_RCC_DeInit()` 会重新使能 SysTick，而"关 SysTick"写在了它前面 | 致命 |
| 2 | IWDG 等待循环死锁 | 初始化顺序反了（先改参数后启动），PVU/RVU 无时钟可清 | 致命 |
| 3 | 硬浮点指令触发 UsageFault | `platform_init()` 漏了 FPU 使能 | 致命 |
| 4 | 热跳转时 PLL 配置被静默忽略 | 写 `PLLCFGR` 前没先关 PLL；且 `if (hse_ok)` 没包住"开 PLL+切 PLL" | 致命 |
| 5 | 回滚永不触发 | `reset_cause()` 是读后即清，却只在 Testing 分支调用 → 标志累积；且首次启动与"按复位"在复位原因上无法区分 | 严重 |
| 6 | SWD 烧写全系列失败 | 杜邦线过长导致信号完整性差 | 阻塞 |

**这 6 条的共同点：都不是逻辑写错，而是「顺序」「时序」「环境」层面的问题 ——
只有真板全链路跑一遍才会暴露。这也是本测试计划存在的理由。**

## 一、升级协议选型（核心结论）

**结论先行：继续用 YMODEM。** 不是因为它更先进，而是因为另外两套方案的
"上位机成本"和"协议复杂度"都远高于它，而 YMODEM 的上位机是白送的。

### 1.1 OpenBLT 用的是 XCP 协议，不是 YMODEM/XMODEM

这是最容易误解的一点。OpenBLT **不用**任何 X/Y/ZMODEM，它用的是
**XCP v1.0（ASAM MCD-1 通用测量与校准协议）**——一个汽车电子领域的标准主从协议。
用于 IAP 时，一次升级的命令序列是：

| XCP 命令 | 作用 |
|---|---|
| `CONNECT` | 建立连接，目标返回协议版本与资源状态 |
| `GET_STATUS` | 查询 Bootloader 状态 |
| `SET_MTA` | 设置内存传输地址（下一个写入目标） |
| `GET_SEED` / `UNLOCK` | Seed/Key 挑战应答鉴权 |
| `PROGRAM_START` | 通知目标准备编程 |
| `PROGRAM_CLEAR` | 擦除指定 Flash 扇区 |
| `PROGRAM` | 分块写入固件数据（最耗时阶段） |
| `UPLOAD` | 回读内存，用于校验 |
| `PROGRAM_RESET` | 编程结束，复位或跳转 |

配套上位机：`MicroBoot`（GUI）、`BootCommander`（CLI）、`LibOpenBLT`（C 库）。
固件格式用 **S-record**（自带地址信息，比裸 bin 好）。

**它的架构确实漂亮**——四层解耦（应用配置 / 目标无关核心 / 目标相关驱动 / 编译器相关），
协议与传输层解耦（同一套 XCP 跑在 RS232 / CAN / CAN FD / USB / TCP/IP / Modbus 之上）。
但对我们来说有两个硬伤：**许可是 GPL（闭源要买商业授权）**，以及 **XCP 协议本身比 YMODEM 重得多**。

### 1.2 MCUboot 根本不做传输，它只管"镜像验证与切换"

这是第二个容易误解的点。MCUboot 是 `transport-agnostic` 的——
它只关心镜像槽位（primary / secondary）、镜像头（header）和尾部（trailer），
**完全不关心固件是怎么传进来的**。

它的串口升级走 **Serial Recovery** 功能，内部实现的是 **SMP（Simple Management Protocol）**
服务端。SMP 是 MCUmgr 管理协议的传输编码，数据用 **CBOR** 序列化。命令集是：

| 组 | 命令 | 作用 |
|---|---|---|
| OS (0) | `echo` | 回显测试 |
| OS (0) | `reset` | 复位设备 |
| IMG (1) | `image list` | 列出镜像槽状态 |
| IMG (1) | `image upload` | 上传固件到槽位 |

上位机是 `mcumgr` CLI（Go 语言写的，Apache-2.0）。
关键代码在 `boot/boot_serial/src/boot_serial.c`（SMP 服务端）和 `boot/zephyr/serial_adapter.c`（串口适配）。

**问题在于**：这套实现与 Zephyr 生态深度耦合——依赖 `flash_map`、设备树、
Zephyr 的工作队列与配置系统。往裸机 STM32 上移植，等于要把 SMP 服务端 + CBOR 编解码 +
串口适配整套搬过来，工作量远超自研一个 YMODEM 接收端。

### 1.3 三套方案横向对比

| 维度 | OpenBLT（XCP） | MCUboot（SMP/CBOR） | **YMODEM** |
|---|---|---|---|
| 下位机实现量 | ~1000-2000 行 | ~1500-2500 行（且耦合 Zephyr） | **~400 行** |
| 上位机 | MicroBoot / BootCommander | mcumgr CLI（Go 工具） | **串口工具原生支持，零开发** |
| 许可 | **GPL v3 或商业授权** | Apache-2.0 | 公开规范，无风险 |
| 协议复杂度 | 高（完整 XCP 栈） | 高（CBOR 编码 + 组/命令体系） | 低（定长帧 + CRC16） |
| 裸机移植难度 | 中（需移植 XCP slave） | **高**（需移植整个 SMP + CBOR） | 低 |
| 跨平台（GD32/CH32） | 许可受限 | 可用但搬运量大 | **无限制** |

**决定性差异是上位机**：OpenBLT 和 MCUboot 都要额外获取上位机工具
（一个受 GPL 约束，一个是 Go 工具链），而 YMODEM 的上位机就是你电脑上
已经装好的 SecureCRT / Xshell / MobaXterm / Tera Term，或者 Linux 下的 `sb` 命令。

### 1.4 因此：协议层继续用 YMODEM，但借鉴它们的设计

## 二、许可分析

| 来源 | 许可 | 能否直接用 |
|---|---|---|
| ST CubeF4 IAP 例程（`ymodem.c` / `flash_if.c`） | **SLA0048** | ❌ 仅限 ST 芯片 |

| **MCUboot** | **Apache-2.0** | ✅ 可用（但架构不匹配） |

### 2.1 ST 官方 IAP 例程：技术上现成，许可上不能用

路径（本机已有）：

```
C:\Users\11846\STM32Cube\Repository\STM32Cube_FW_F4_V1.27.1\
  Projects\STM324xG_EVAL\Applications\IAP\IAP_Main\
    src\ymodem.c      18930 B   ← YMODEM 收发完整实现
    src\flash_if.c     8537 B   ← Flash 擦除/编程封装，含 S0-S11 地址宏
```

`STM324xG_EVAL` 用的就是 **STM32F407**，与 F405 同系列同 Flash 布局，
`flash_if.h` 连扇区地址宏和 `APPLICATION_ADDRESS` 都写好了。**技术上零改动可用。**

但 Cube 包根目录 `Package_license.md` 声明的是 **SLA0048**，第 4 条原文：

> ...**must be used and execute solely and exclusively on or in combination with**
> microcontroller or microprocessor device manufactured by or for STMicroelectronics

即**只能在 ST 芯片上运行**。移植 GD32 / CH32 违反此条款。

> 说明：`flash_if.c` 等文件头部声明的是
> "licensed under terms that can be found in the LICENSE file in the root directory"，
> 指向的就是包根目录那份 SLA0048，最终仍受第 4 条约束。

### 2.2 OpenBLT：双重许可，默认 GPL

官网原文（`github.com/feaser/openblt`）：

> OpenBLT is offered under a **dual licensing model**. The default license is the
> **GNU GPL**. If you plan on integrating OpenBLT into your **closed source project**,
> a **commercial license** can be obtained.

- 若你的项目开源（GPL 兼容）→ 可自由使用
- 若产品要闭源交付 → **必须购买商业授权**，否则整个产品都要以 GPL 开源

（注：网上有文章称 OpenBLT 是"BSD 风格宽松许可、可商用"，**这是错误的**，
以官网 README 的双重许可声明为准。）

### 2.3 MCUboot：Apache-2.0，宽松但架构不匹配

Apache-2.0，商用友好（保留声明即可）。可安全借鉴其设计思想与算法。
但如 1.2 所述，它的传输层实现无法低成本搬到裸机上。

### 2.4 结论：协议层自研

不是"不想复用"，是"没有可用的合规实现"：ST 的许可锁死在 ST 芯片，
OpenBLT 的 GPL 会传染，MCUboot 的架构搬不动，MIT 那份只有发送端。

**但"自研"不等于"从零发明"**：YMODEM 是 Chuck Forsberg 公开的规范，
按规范实现不侵权；阅读 ST 的实现来理解协议细节也不侵权（**复制代码才侵权**）。

**顺带说明：分层架构天然规避了许可风险。**
`target/` 层本来就不跨平台复用（各芯片寄存器、页大小、编程粒度都不同），
STM32 版用 HAL 完全合规（SLA0048 允许在 ST 芯片上使用）；
而需要跨平台共用的 `core/` 层，恰好是我们的自研代码。

| 层 | 跨平台复用？ | 代码来源 | 许可风险 |
|---|---|---|---|
| `core/` | ✅ 要复用 | 自研（CRC、meta 已完成） | 无 |
| `port/` | ✅ 要复用 | 自研接口 | 无 |
| `target/stm32f4/` | ❌ 平台专属 | HAL 库 | 无 |
| `target/gd32f30x/` | ❌ 平台专属 | GD32 官方库 | 无 |
| `target/ch32*/` | ❌ 平台专属 | CH32 官方库 | 无 |

## 三、值得借鉴的设计（思想可自由使用）

调研这两个项目的最大收获其实是**设计思想**，这部分不受版权保护，可以放心采用。

### 3.1 采自 OpenBLT

| 设计 | 说明 | 本项目是否采用 |
|---|---|---|
| **Backdoor 入口** | 复位后固定时间窗内监听特定触发，强制进入 Bootloader | ✅ 已采用（300ms 窗口） |
| **协议与传输层解耦** | 同一套协议可跑在不同物理层上 | ✅ 已采用（core / port 分层） |
| **启动时校验合法性** | 每次上电校验用户程序，无效则留在 Bootloader | ✅ 已采用（状态机 + 可选 CRC32） |
| **伪向量表 + 中断重路由** | Bootloader 掌握主向量表，跳转后重路由到用户向量表 | ❌ 不采用——APP 直接设 `SCB->VTOR` 更简单，现代 Cortex-M3/M4 原生支持 |
| **S-record 格式** | 固件自带地址信息 | ⏸ 暂不采用——先用裸 bin + 固定地址，后期可扩展 hex/srec 解析 |
| **Seed/Key 鉴权** | 防止未授权刷写 | ⏸ 预留钩子，暂不实现 |
| **Checksum 写入** | 刷写完成后写入校验值 | ✅ 已采用（配置区记录 CRC32） |

### 3.2 采自 MCUboot

| 设计 | 说明 | 本项目是否采用 |
|---|---|---|
| **`image_ok` 确认语义** | APP 自检通过后才"转正"新固件，否则下次复位回滚 | ✅ 已采用（`TESTING` → `VALID`） |
| **trial boot 自动回滚** | 新固件试运行，失败自动退回旧固件 | ✅ 已采用（启动计数，连续 3 次未确认则作废） |
| **image trailer 元数据** | 镜像尾部存放状态与校验信息 | ✅ 变体采用——放在独立配置扇区（因 Flash 受限，无 A/B 空间） |
| **A/B 双槽 + swap** | 最彻底的防变砖方案 | ❌ 装不下（需 2×880KB，本芯片仅 1MB） |

### 3.3 我们相对两者的额外设计

- **配置区日志式槽位轮转**：128KB 切成 2048 个 64B 槽，状态变更只追加写 64 字节。
  OpenBLT 与 MCUboot 都没有针对"每次上电记启动计数"这一场景做优化，
  直接写会导致每次上电都擦扇区（1 秒延迟 + 寿命消耗）。
- **原子提交的显式顺序约束**：先置 `DOWNLOAD` 再擦 APP 区，写进 README 作为强制约束。
- **编译期分区自检**：改错地址直接编译不过。

## 六、ROM 占用预算（16KB 硬约束）

| 模块 | 预估 | 说明 |
|---|---|---|
| YMODEM 状态机 | 2-3 KB | 自研精简实现 |
| CRC16 + CRC32 | 0.5 KB | 含 nibble 表 |
| meta + verify + session + boot | 1.5-2 KB | |
| 跳转 / 看门狗 / 时基 | 1 KB | |
| UART 驱动 | 1-2 KB | 视中断/DMA 方案 |
| Flash 驱动 | 1-2 KB | |
| 调试输出（可选） | 1-2 KB | 若用 `printf` 家族，实测常超预期 |
| **小计** | **8-13 KB** | |
| 余量 | 3-8 KB | |

**风险点**：`BL_DEBUG_LOG` 打开时若链接了完整 `printf`（含浮点），可能一次吃掉 3-4KB。
必要时改用精简 `bl_printf`（只支持 `%d / %x / %s / %c`）。
编译后必须查 `.map` 确认，这是 P8 的硬性验收项。
