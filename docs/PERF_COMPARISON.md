# 性能对比：Bootloader-Everywhere vs 开源 IAP / OTA 方案

> 本文只做两件事：**把账算准**（按各协议的公开规范逐字节推算），**把话说实**（哪些是我们赢的、
> 哪些是我们输的、差距值不值得改）。
>
> 我们的数字全部来自真板实测（STM32F401RET6）；他们的数字来自各自官方文档或规范，
> 少数来自第三方实测的地方会明确标注。凡是我按规范推算而非直接引用的，都标了「推算」。

---

## 0. 一句话结论

| | |
|---|---|
| **纯协议效率** | YMODEM-1K 与我们几乎同档（0.59% vs 7.23%）；esptool 因为用 **16 KB 大块** 做到 0.21%，是这一项的天花板 |
| **但这不是瓶颈** | 在 115200 下，把协议从「我们的 7.23%」换成「esptool 的 0.21%」，200 KB 只快 **0.6 秒**（22.9 → 22.3）。同一台板子把波特率提到 921600，快 **16.4 秒** |
| **我们的真实短板** | 高速下被**主机往返（约 5 ms/帧）+ 同步写 Flash（2.05 ms/帧）**卡住：921600 时只跑到线速的 34%；体积小、可断点续传、校验强度是我们赢的地方 |
| **值得改的只有两件** | ① 提波特率（改动 2 行，收益 3.5 倍）② 加大块到 1010（改一个常量，省 3.6%，高速下省更多） |

## 1. 我们的实测基线（真板，STM32F401RET6）

### 1.1 端到端耗时（115200 8N1，块 512 B）

| 固件 | 帧数 | START（擦除） | DATA | END | **合计** |
|---|---|---|---|---|---|
| 2 KB | 5 | 0.21 s | 0.22 s | 0.00 s | **0.43 s** |
| 64 KB | 128 | 1.12 s | 6.66 s | 0.03 s | **7.81 s** |
| 200 KB | 400 | 2.06 s | 20.84 s | 0.07 s | **22.97 s** |
| 496 KB（极限） | 992 | 3.78 s | 51.79 s | 0.18 s | **55.75 s** |

### 1.2 波特率杠杆（实测，临时改宿主 `usart.c` 验证后已还原）

| 波特率 | 200 KB 合计 | 相对 115200 | 有效率（线速 200KB/线速） |
|---|---|---|---|
| **115200** | **22.90 s** | 1.0x | 77% |
| **921600** | **6.54 s** | 3.5x | 34% |
| **2000000** | **5.34 s** | 4.3x | 19% |

### 1.3 模型可信度自检

| 项 | 值 |
|---|---|
| 200 KB 理论纯线上时间（按帧长推算） | 19.06 s |
| 实测数据阶段 | 20.84 s |
| **协议效率 = 理论 / 实测** | **91%**（余下 9% 是主机往返 + 写 Flash + 每帧应答的固定开销） |

## 2. 逐字节的帧开销（按各协议公开规范推算）

| 协议 / 配置 | 有效载荷 | 线上字节 | 开销 | 构成 |
|---|---|---|---|---|
| **我们（0xA5 帧，块 512）** | 512 | 549 | **7.23%** | 7 外壳 + 14 头 + 16 应答 |
| 我们（块 1010 = 载体上限） | 1010 | 1047 | 3.66% | |
| 我们（块 512、取消应答·仅参考） | 512 | 533 | 4.10% | |
| **YMODEM-1K** | 1024 | 1030 | **0.59%** | `STX+seq+~seq+data+CRC16` + ACK 1 B |
| XMODEM（128 B 块） | 128 | 134 | 4.69% | |
| **esptool（块 16384，stub 默认）** | 16384 | 16418 | **0.21%** | 8 头 + 16 载荷头 + 10 应答 |
| esptool（块 1024，小 RAM 设备） | 1024 | 1058 | 3.32% | 同上 |
| mcumgr / SMP（默认 NETBUF 384） | 376 | 510 | **35.64%** | Base64 1.37x + 128 B 行分片 |
| mcumgr / SMP（NETBUF 调到 4096） | 4088 | 5517 | 34.96% | Base64 的膨胀与块大小无关 |
| UDS / ISO-TP @经典 CAN（8 B 帧） | 7 | 8 | 14.29% | ISO 15765-2 的 PCI 占 1 字节 |
| UDS / ISO-TP @CAN FD（64 B 帧） | 62 | 64 | 3.23% | PCI 占 2 字节 |

**依据**：esptool 的 `_DATA` 载荷头是 `[len:4][seq:4][zeros:8]`，块大小官方文档明示
「esptool uses 16 KB which gives good performance when used with the stub loader」；
mcumgr 的 `MCUMGR_TRANSPORT_NETBUF_SIZE` 默认 384（解码后），UART 传输用 Base64 +
≤128 字节行分片，线上膨胀约 **1.37x**（Base64 的 4/3 再加行帧）；
YMODEM / XMODEM / UDS 部分按各自规范逐字段累加。

## 3. 端到端对比：200 KB 固件（纯传输，115200，不含擦除与握手）

| 协议 / 配置 | 推算耗时 | 线上占空比 |
|---|---|---|
| YMODEM-1K | 17.9 s | 99.4% |
| esptool（块 16384） | 18.5 s | 96.0% |
| 我们（块 1010） | 18.4 s | 96.4% |
| esptool（块 1024） | 18.4 s | 96.8% |
| **我们（块 512，实测 22.9 s）** | 19.1 s | 93.3% |
| mcumgr / SMP（默认或调大） | 24.1 - 24.4 s | 73 - 74% |

**这张表最重要的一行**：把我们的协议换成全场最省的 YMODEM-1K，
200 KB 也只从 19.1 s 降到 17.9 s（**1.2 秒**）；而实测我们花了 22.9 s，
其中 2.1 s 是擦除、0.4 s 是主机往返与写 Flash 的累计开销。
**换成别人的协议能省的那 1.2 秒，在本项目里远不如把波特率提上去划算。**

## 4. 不只是速度：能力对比

| 能力 | 我们 | YMODEM-1K | esptool | mcumgr/SMP | OpenBLT(XCP) |
|---|---|---|---|---|---|
| 帧校验 | CRC8（检出全部 ≤8 bit 突发错误） | CRC16 | XOR 0xEF（官方文档自称「不足以保证正确」） | 每片 CRC16 / 整包 hash | 可配置 checksum / CRC |
| 整镜像校验 | **CRC32 + 逐帧回读 Flash 重算** | 无（只有帧 CRC） | 末尾 SPI_FLASH_MD5（官方推荐） | SHA-256（MCUboot 侧） | 有 |
| 帧级回读验证 | **有**（写后读回重算，覆盖 Flash 静默写失败） | 无 | 无（官方口径：每包仅 XOR，靠末尾 MD5 兜） | 无 | 无 |
| **断点续传** | **任意 512 B 边界**（NAK 带期望地址） | **不支持**（失败必须整片重传） | 整块重传（块 = 16 KB） | 分片重传 | 有（XCP 层） |
| 错误码分级 | **16 个** | 无（只有 NAK/CAN） | 有（约 20 个） | 有 | 有 |
| 传输前完整性预检 | **START 先验向量表，不通过不擦除** | 无 | 无 | 有（镜像头签名） | 无 |
| 提交原子性 | **向量表最后写**（提交 = 写 8 字节） | 无 | 无 | MCUboot swap（需要双分区） | 无 |
| 加载器/协议层 ROM | **约 500 B**（库本体 7.9 KB） | 约 3 KB（第三方估） | 100+ KB（ROM 引导 + stub） | 数十 KB（CBOR + base64） | 数十 KB（XCP 栈） |
| 上位机依赖 | 我们自己的网页 / 脚本 | **任何串口工具** | esptool | mcumgr CLI | MicroBoot |
| 压缩 | 无 | 无 | **deflate 默认开启** | 无 | 无 |
| 收发与写 Flash 重叠 | 无（停等） | 无（停等） | **有**（stub 边收边写） | 无 | 部分 |

**几个要点**：

- **YMODEM 最大的优势是「谁都能刷」**——SecureCRT / Tera Term / minicom 直接支持。
  这是换协议时**主动放弃**的东西，代价真实存在。
- **esptool 的 0.21% 不是因为协议优雅，而是因为 16 KB 块 + 边收边写**。
  它的 XOR 校验弱到官方文档自己承认不够，只能靠末尾 MD5 兜。
- **OpenBLT 的 UART 演示默认 57600**，主机工具 `BootCommander` 的波特率选项列的是
  `9600 / 19200 / 38400 / 57600 / 115200`——它的速度优势在 CAN / 以太网上，不在串口。
- **mcumgr 的 Base64 是硬成本**：把缓冲从 384 调到 4096 也只从 35.6% 降到 35.0%。
  它的强项是「多镜像槽 / 设备信息查询 / 多传输层」，不是吞吐。

## 5. 优劣势分析

### 5.1 我们赢在哪（都有实测或规范依据）

1. **断点续传的粒度最细**。任何 512 字节都能续传；YMODEM 只能整片重来，
   esptool 最小重传单位是 16 KB 块。链路一抖动，这个差距立刻体现。
2. **校验是三层且层层独立**：帧 CRC8（查传输错）→ 从机**读回 Flash 重算 CRC32**
   （查 Flash 静默写失败，这是别人都没有的一层）→ 末尾整片 CRC32（查全局）。
   而且有实测证据：单字节突变 54 万次**零漏检**，随机流 32 MB **零假帧**，
   对抗流假帧率约 **1/458752**。
3. **传输前预检**：`START` 先验向量表和长度，不通过**根本不擦除** ——
   边界测试 E1-E14 全部验证了「被拒绝时 APP 区未被改动」。
4. **协议层与业务彻底分离**：`protocol.{h,cpp}` 只依赖 `stdint.h`，
   可以整对拷到 APP / 上位机 / 别的 MCU 工程（这是为将来「APP 侧也讲这套协议」铺的路）。
5. **体积**：整份固件 11.1 KB（协议层约 500 B），16 KB 区余量 5.2 KB。
   对照 OpenBLT / MCUboot 都是数十 KB 起。
6. **上位机自检三处同源**：`tools/test_protocol.cpp`（C）、`proto.py selftest`（Python）、
   JS 的 `tools/test_protocol_js.mjs` 用**同一组测试向量**，任何一端口径漂了立刻暴露。
   固件侧**刻意不带自检**（见 `AGENTS.md` §7，省 248 B ROM）—— 它的一致性由端到端
   强制保证：升级时主机与从机各算一遍整片 CRC32，必须逐位相同才提交。

### 5.2 我们输在哪（这才是要正视的）

1. **帧开销 7.23%，是 YMODEM 的 12 倍、esptool（16 KB 块）的 34 倍。**
   代价的构成很清楚：块 512（太小）+ 每帧 16 字节应答 + 21 字节帧头。
2. **高速下严重偏离线速**：921600 时只跑到线速的 **34%**，2 Mbps 时 **19%**。
   原因是每帧的固定开销与波特率无关，按帧数累积：

   | 波特率 | 线上/帧 | 主机往返 | 写 Flash | 实测/帧 | 线速利用率 |
   |---|---|---|---|---|---|
   | 115200 | 47.7 ms | ≈2.2 ms | 2.05 ms | 52.1 ms | 91% |
   | 921600 | 6.0 ms | ≈5.0 ms | 2.05 ms | 13.1 ms | 46% |
   | 2 Mbps | 2.75 ms | ≈5.3 ms | 2.05 ms | 10.1 ms | 27% |

   **主机侧的约 5 ms/帧是本项目真正的天花板**（USB 串口 latency timer + Python 解析），
   Flash 写的 2.05 ms/帧是第二道。两者都与波特率无关。
3. **没有压缩**。esptool 默认 deflate。固件里重复字节很多，通常能压 30-50%——
   这一项如果做，等效于把波特率提高 1.5-2 倍。代价是设备端要 inflate（约 2-3 KB ROM）。
4. **停等模型不能把写 Flash 藏起来**。esptool 的 stub 边收边写，我们写 Flash 时线路是空闲的。
5. **没有生态**：只有我们自己的网页和脚本能刷（这是主动取舍，见 5.3）。

### 5.3 被主动放弃、需要明确记账的

- **「任何第三方串口工具都能刷」**（YMODEM 的唯一优势）。换掉它是为了可读的帧格式、
  精确的错误码与断点续传，这笔交易在设计文档 §0「代价」里已记账。
- **不支持压缩 / 不做首部签名 / 不做双分区**（L3 工业级能力）。当前场景是人站在板子前刷机，
  不需要；真需要时是另一次设计。

## 6. 值得做的优化（按「收益 ÷ 成本」排序）

| # | 优化 | 成本 | 200 KB 收益 | 说明 |
|---|---|---|---|---|
| 1 | **波特率 → 921600** | 宿主 `usart.c` 改 1 个数 + 上位机 `--baud` | **−16.4 s（3.5x）** | 已实测跑通且整片 CRC32 校验通过。**唯一的数量级杠杆** |
| 2 | **块 512 → 1010** | 改 `BL_BLOCK_SIZE` 一个常量 | −0.6 s @115200；**−1.8 s @921600** | 高速下收益放大 3 倍（帧数减半 → 主机往返与写 Flash 的次数都减半） |
| 3 | 降主机往返 | 关 USB 串口 latency timer / 上位机改批量读写 | 最多 −2 s @921600 | 5 ms/帧里有相当部分是驱动侧等待 |
| 4 | 压缩（deflate） | 设备端 inflate，约 2-3 KB ROM | 等效 −30%~−50% | 16 KB 区余量 5.2 KB，勉强够；需先评估 |
| 5 | 边收边写（DMA 双缓冲） | 较大改动 | −2.05 ms/帧 | 只在块变大后才有意义（块 1010 时占 4%） |

**建议**：只做 **1 和 2**（各改一行），收益覆盖 200 KB 的 80%；3 顺手；
4 和 5 等真需要再评估。**当前 115200 + 块 512 是定案配置，不擅自改。**
