## 0. 现行设计（已定稿部分）

### 0.1 载体帧（全部命令共用同一种帧）

```
[0xA5] [ID] [CMD] [DataLen:2 LE] [Data ≤1024] [CRC8] [0x03]
  1B    1B   1B   └── 小端 ──┘   └── N ──┘     1B     1B       共 8 + N 字节
```

| 字段 | 规则 |
|---|---|
| `0xA5` | 帧头（兼作波特率探测图案：连发 `0xA5`） |
| `ID` | **从机地址**；`0x00` = 广播（从机收到广播**不回话**）。将来地址存一个 Flash 扇区 |
| `CMD` | **bit7 = 方向位**（0 = 主→从；1 = 从→主）；bit0-6 = 命令码（128 个） |
| `DataLen` | 小端，**≤1024**；`= 0` 合法（无数据命令）；**>1024 立刻丢弃并回错**（不能等收完） |
| `CRC8` | 变体统一为 **CRC-8/SMBUS**（poly 0x07 / init 0x00 / 无反射 / xorout 0x00）；覆盖 `[ID .. Data 末尾]`，**不含 `0xA5` 与 `0x03`** |
| `0x03` | 帧尾。不是冗余：它与 CRC8 一起把「丢字节后重新对齐的误接受率」压到 1/65536 |

**应答帧与请求帧格式相同**，只是 `CMD` 的 bit7 置 1，且**总长 ≤ 32 字节**（数据区 ≤25）。

### 0.2 从机的行为约束

- **从机只有被动应答**：收到询问才回，**不主动发任何帧** → 主机在发数据流时无需监听 RX
- 因此**进度与错误检测必须靠主机 POLL**：`POLL → 应答 [状态:1][已写入偏移:4][期望偏移:4]`
- 波特率**定死**（不做握手协商），但值可以选高一些（见 0.4）

### 0.3 传输层：接收方式（2026-10-06 修订）

> **2026-10-06 修订：DMA 从「必需」降为「可选」。**
> `DATA` 改为停止-等待后，从机写 Flash 的那 2.05 ms 落在「主机正在等应答」的窗口里，
> 线路上零字节到达，因此「总线停摆导致失序丢字节」这个风险的前提消失了。
> 停等模型下用**中断逐字节接收**即可（CPU 占用约 3%），代码比环形 DMA + 流式解析少得多。
> 下面各节保留，作为「将来把波特率提到 460800 以上」时的参考。

**真因**：STM32F4 在写/擦 Flash 期间**总线停摆**（RM0090：*code or data fetches
cannot be performed while a write/erase operation is ongoing*）。我们的代码与向量表
都在 Flash 里 → **ISR 自身取指也被 stall**，所以「只开中断」救不了；只有 **DMA** 能
（`USART->DR → SRAM` 走 bus matrix，不碰 Flash 阵列）。

| 波特率 | 字节间隔 | 中断收余量 | 结论 |
|---|---|---|---|
| 115200 | 86.8 µs | 5.4x | 可行 |
| 460800 | 21.7 µs | 0.3x | 不安全 |
| 921600 | 10.9 µs | — | 必然丢 |

形态：**环形 DMA（2 × 1024 B 双缓冲）** + 半传输/传输完成中断 + **流式解析状态机**
（正常时「半区 = 一帧」）。不用 HAL 的 `ReceiveToIdle`（连续流里没有 IDLE），
也不用「精确长度 DMA」（重装间隙会丢字节）。

> 注：**YMODEM 今天没暴露这个问题，是因为它是停等协议**——从机在等 ACK 期间写 Flash，
> 那段时间线上无字节。所以这是**取消逐块 ACK 之后才引入的前置条件**，不是修 bug。

### 0.4 波特率：最大的收益点在这

Flash 写吞吐上限约 **244 KB/s**（16 µs/字 × 256 字/KB），而 115200 只有 11.5 KB/s
—— **21 倍余量被浪费**。传 200 KB 固件：

| 波特率 | 200 KB 耗时 |
|---|---|
| 115200 | 17.4 s |
| 460800 | 4.3 s |
| **921600** | **2.2 s** |

84 MHz PCLK2 下：921600 分频误差 +0.02%，2 Mbps 正好整除（0%）。

### 0.5 IAP 命令（2026-10-06 修订：DATA 改为「一应一答」）

> 本节相对上一版有两处方向性变化：**`DATA` 从单向流改为请求-应答**（每帧都有应答），
> **`POLL` 取消**（每帧都有应答之后，不再需要轮询探状态）。
> `SP` / `PC` 确定放在 `START` 载荷里。

#### 0.5.1 命令与载荷

| 命令 | 方向 | 载荷 | 说明 |
|---|---|---|---|
| `START` | 主→从 | `size:4` `crc32:4` `sp:4` `pc:4` | 镜像总长 / 整镜像 CRC32 / 向量表前两字 |
| `START` | 从→主 | `status:1` `blockSize:2` | 校验向量表 → 擦除 → 才应答（约 4 秒，见 0.5.6） |
| `DATA` | 主→从 | `addr:4` `total:2` `index:2` `vlen:2` `cumCrc32:4` `data`（≤512） | 见 0.5.2 |
| `DATA` | 从→主 | `status:1` `cumCrc32:4` `nextExpectedAddr:4` | **每帧一应一答**；`cumCrc32` 是从机侧的实际值 |
| `END` | 主→从 | 空 | 请求提交 |
| `END` | 从→主 | `status:1` `writtenLen:4` | 回读校验 + 写回 SP/PC 之后、跳转之前 |
| `STATUS` | 主→从 | 空 | **仅用于异常恢复**（从机复位后主机重新对表），正常流程不用 |
| `STATUS` | 从→主 | `status:1` `writtenLen:4` `nextExpectedAddr:4` | |

`DATA` 帧 = 6（载体外壳）+ 14（头部）+ N（≤512） = 最大 **532 字节**；
`DATA` 应答帧 = 6 + 9 = **15 字节**。

> **字节序（两端必须一致）**：载体 `DataLen` 与 Data 内**所有多字节字段**
> （`size` / `crc32` / `sp` / `pc` / `addr` / `total` / `index` / `vlen` / `cumCrc32` /
> `blockSize` / `nextExpectedAddr`）**一律小端**。STM32 原生小端，PC 端用
> `int.from_bytes(..., 'little')` / `DataView.setUint32(0, v, true)`。

#### 0.5.2 DATA 的五条规则

（规则一至四给数据与写入，规则五给寻址与总线纪律。）

**规则一：先校验、后写入。** 从机先算 `候选累积 = update(已验累积, 本帧 data)`，与帧内
`cumCrc32` 比对，一致才写 Flash。原因：Flash 只能 1→0、不能覆盖，若先把坏数据写进去，
纠正时必须**整扇区擦除**再重传，代价从「重传 1 帧」变成「重传 16 帧以上」。反过来还白拿
一个能力 —— 前面每一帧都已验证过，所以**一旦不符，错的一定是本帧**。

**规则二：地址严格连续。** 从机只接受 `addr == 期望地址`：

- `addr < 期望地址` → 视为**重复帧**（应答丢失导致的主机重发）：**不重写**，原样重发上一次应答（幂等）
- `addr > 期望地址` → 回 `NAK(期望地址)`，主机从那里续发

**规则三：三个冗余字段必须交叉校验，不一致即报错。**

`total`（总包数）、`index`（包号）、`vlen`（本包有效长度）都能由 `addr` 和载体 `DataLen`
推出。它们存在的意义是**多一个独立证据**（检测串扰、越权写入、错位），不是提供信息。因此
判据必须钉死：

```
index == (addr - appBase - 8) / blockSize        // 不符 → 0x0E
vlen  == DataLen - 14                            // 不符 → 0x0E
total == ceil((size - 8) / blockSize)            // 不符 → 0x0E
addr  == appBase + 8 + index * blockSize         // 不符 → 0x07
```

**任何一条不符即拒绝本帧、回错 —— 绝不「挑一个相信」。** 冗余的价值在于多一个独立证据；
一旦允许「以某个字段为准」，它就退化成纯粹的 6 字节开销。

**规则四：应答里的 `cumCrc32` 必须由从机读回 Flash 计算。**
若从机只对「收到的字节」累加，那它与主机在帧里发来的 `cumCrc32` 必然逐字节相同（同一串字节
在两端各算一次），**比对毫无信息量**。改成写完之后读回 Flash、对这 512 字节累加，这条 CRC32
认证的就是「**真正落到 Flash 里的内容**」—— 它同时覆盖 CRC8 的漏检（约 1/65536 每帧）与
Flash 静默写入失败两类问题。成本约 30 µs（512 字节读回 + CRC32）。

**规则五：ID 匹配失败必须「静默丢弃」，不能回错。**

载体第 2 字节是从机地址，有三种情况要分开处理 —— 混在一起会在**多从机总线**上出事：

| 收到的 ID | 从机动作 | 为什么 |
|---|---|---|
| `== 本机地址` | 正常处理，正常应答 | — |
| `== 0x00`（广播） | **执行，但不回话** | 多个从机会同时应答 → 撞车 |
| 其他（别人的地址） | **完全静默丢弃**，连错误都不回 | 若回 NAK，会与"被寻址那个从机"的应答撞车 |

所以错误码 `0x03` 只覆盖「地址在**本机语义内**不对」（如 `addr` 落在 APP 区外），
**不覆盖 ID 不含本机**。同理，重同步失败、CRC8 错、帧尾错也都**静默丢弃** ——
总线上别人的帧不该引起本机任何动作。

#### 0.5.3 CRC32 的覆盖域

**统一定义为「实际写进 APP 区的字节」= 镜像 `[8, size)`。**

- 主机：`crc32(file[8:])`
- 从机：对每帧读回的 `data` 累加（数据流从 `appBase + 8` 开始，见 0.5.4）
- `END` 回读校验：`crc32Flash(appBase + 8, size - 8)`

前 8 字节（SP/PC）不进 CRC32：它由帧 CRC8 保护，且在 `START` 时就会被 `vectorsSane()` 检查。
**载体外壳（`0xA5` / `CRC8` / `0x03`）与 DATA 头部字段（`addr` / `total` / `index` / `vlen`）
都不进 CRC32，只由 CRC8 保护** —— 这正是 0.5.2 规则三存在的理由：头部一旦漏检，地址可能被写歪。

#### 0.5.4 数据流起点与提交点

因为 `SP` / `PC` 由 `START` 携带，**DATA 数据流从 `appBase + 8` 开始**（即镜像的 `[8, size)`）。
好处：写路径零特例，不需要「第 0 帧跳过前 8 字节」这类分支。

提交仍沿用现有的「向量表最后写」：

```
接收全程只写 [appBase+8, appBase+size)
  → END 时回读校验 CRC32
  → 写 appBase（SP）
  → 写 appBase+4（PC）        <= 提交点
```

任何时刻掉电 → SP/PC 仍是 0xFF → 向量表非法 → 上电停 IAP 可重刷。

#### 0.5.5 从机状态机

```
IDLE ──START(向量表合法)──> 擦除 ──> RECEIVING ──END(回读校验通过)──> 提交 ──> 应答 ──> 跳 APP
                                        │
              任一帧失败 ────────────────┘   回 NAK，等待主机从 nextExpectedAddr 重发
```

`IDLE` 只接受 `START`；此时收到 `DATA` 回 `0x06`（状态错误）。

**两条状态机细则（都是为了消掉"卡住"的可能）**：

1. **`START` 在任意状态都接受，并强制重置状态机**（含正在 `RECEIVING` 时）。
   理由：主机中途放弃后，若从机要等满 30 秒空闲超时才回 `IDLE`，主机的下次升级会
   白等 —— 直接 `START` 就该能重新开始（`START` 本身会重新擦除，语义上等价于"从头来"）。
2. **`END` 校验失败时，从机保持在 `RECEIVING`，不提交、不跳转**，回 `NAK(期望地址)`
   或对应错误码。因为数据都还在 Flash 里，主机可以重传坏掉的那一帧再重发 `END`，
   不必整片重来。

#### 0.5.6 时序与超时

| 环节 | 耗时 | 主机超时 |
|---|---|---|
| `START` 校验 + 擦除（200KB 覆盖区） | 约 3.75 秒（16K×3 + 64K + 128K） | **≥ 8 秒** |
| 一帧 `DATA`（532 B 帧 + 15 B 应答） | 46.2 + 2.05（写）+ 1.3（应答）≈ 49.6 ms，再加主机延迟 | 建议 **≥ 200 ms** |
| `END` 回读校验 200KB | 约 24 ms | 2 秒 |

200 KB 固件（400 帧）总耗时：主机往返延迟 2 ms → 约 **20.6 秒**；延迟 5 ms → 约 21.8 秒。
（对照：纯单向流为 18.3 秒，YMODEM 停等为 20.8 秒。也就是说**这一改动把线上开销拉回 YMODEM
水平** —— 换来的是可读的帧格式、精确的错误定位与可扩展的命令空间。）

#### 0.5.7 错误码

| 码 | 含义 | 码 | 含义 |
|---|---|---|---|
| `0x00` | 成功 | `0x08` | 累积 CRC32 不符 |
| `0x01` | 帧 CRC8 错 | `0x09` | 擦除失败 |
| `0x02` | 长度非法（>1024） | `0x0A` | 写入失败 |
| `0x03` | ID 或地址不匹配 | `0x0B` | 回读校验失败 |
| `0x04` | 未知命令 | `0x0C` | 向量表非法 |
| `0x05` | 参数非法（size 越界） | `0x0D` | 总 CRC32 不符 |
| `0x06` | 状态错误（未 START 就来 DATA） | `0x0E` | 冗余字段不一致 |
| `0x07` | 地址不连续 | `0x0F` | 回读与写入内容不一致 |

#### 0.5.8 已定案（2026-10-06）

| 项 | 定案 | 说明 |
|---|---|---|
| 重传上限 | **5 次** | 同一帧连续重试 5 次仍失败 → 主机中止本次升级 |
| 接收方式 | **中断（逐字节）** | 停等模型下 DMA 非必需（见 §0.3）。CubeMX 里 `NVIC.USART1_IRQn=true` 已使能，不必改配置 |
| `END` 应答语义 | **校验通过 + 正在提交 = 下载完成** | 不依赖 APP 侧确认 |
| `RECEIVING` 空闲超时 | **30 秒** | 30 秒内无任何**有效帧**（ID 匹配且 CRC8 通过）→ 回 `IDLE`。避免主机崩溃/拔线后从机永久卡在中间态 |

**关于 END 语义**：用户明确指出语义边界就在「下载完成」——本流程的职责是"把固件完整、
正确地放进 APP 区"，这件事在 END 应答时已经达成。跳转及其之后的运行状态不属于下载流程；
若跳转后 APP 起不来，那是固件的问题，用 PC0 按键重新进 IAP 即可。

**但有一个实现上的硬顺序**（否则应答发不出去）：

```
校验通过 → 发 END 应答 → 等 TC（发送完成标志）→ 关中断 → 跳转
                              ↑ 必须等这一位，否则应答还没出串口就跳走了
```

**已知代价**：主机只能确认"固件已写入且校验通过"，无法确认"APP 真的跑起来了"。
这是当初删掉「看门狗自恢复」之后的取舍，恢复手段是按住 PC0 重进 IAP。

## 0.6 实现要点与风险清单（开工前必读）

### 0.6.1 中断接收的形态：中断只搬字节，主循环干活

```
USART1_IRQHandler()              中断上下文，越快越好
  └─ 读 SR/DR → 塞进环形缓冲 → 退出        （只做这些）

主循环（IAP 状态机）              普通上下文
  └─ 检测「整帧就绪」→ 校验 CRC8 → 写 Flash → 读回算 CRC32 → 发应答
```

**为什么不在中断里写 Flash**：写 512 B 要 2.05 ms，期间 CPU 被 Flash 控制器 stall，
**SysTick（时基）也停** —— 时基停会让所有超时判断失准。中断只做搬运，长事务交给主循环。

CRC8 也放主循环（1032 字节 = 8256 次循环 ≈ 0.5 ms，占一帧时间的 1%），不必抢进中断。

### 0.6.2 ★ 累计 CRC32 必须「增量」累计，且只在帧被接受后更新

**不能每帧从 `appBase+8` 重算** —— 那是 O(n²)：200 KB 固件 400 帧，累计要算约 40 MB 的 CRC，
最后一帧单独要重算 200 KB，传输时间被拖垮。

正确做法：维护一个**运行中的 CRC32 状态**，每帧把「从 Flash 读回的 512 字节」喂进去：

```
收帧 → 校验头部 → 写 Flash → 读回这 512 B
     → crc32Running = crc32Update(crc32Running, 读回的 512 B)
     → 回应答 { status, crc32Running, nextAddr }
```

**关键约束：只有帧被接受并写入后才 update。** 被拒绝的帧（CRC 错、地址不对）绝不能污染
这个状态 —— 否则状态与 Flash 实际内容永久失配，之后每一帧都对不上。

CRC32 是线性的：只要按严格递增顺序喂字节，增量结果与全量重算一致。

### 0.6.3 重传的幂等：从机要保存「上次应答」

停等 + 可靠传输必然出现这种情况：**从机写完了、应答也发了，但应答在回程丢了**，
主机超时重传同一帧。此时从机看到 `addr == 已写入的末尾`：

```
addr == nextAddr - blockSize   → 重复帧：不重写 Flash（省 2 ms），直接重发上次的应答
addr == nextAddr               → 正常，继续
addr 其它                       → 回 NAK(期望地址)
```

所以从机要保存 `lastAck`（`status` + `crc32Running` + `nextAddr`），约 9 字节状态。
**这是「从机只有被动应答」这个模型下唯一的可靠恢复手段** —— 没有它，一次应答丢失就要重来整片。

### 0.6.4 写 Flash 期间到达的字节：允许丢，靠重传补

写 Flash 的 2.05 ms 里 Flash 总线停摆 → **中断也进不来**（RM0090）。此时线路上若有字节
（噪声、或主机异常提前发的帧），会产生 ORE 溢出并**丢失**。这是**可接受**的：
解析器丢字节后会在下一个 `0xA5` 重新同步（CRC8 + 帧尾把误接受率压到 1/65536）。
停等模型下主机本来也不会提前发。

**两条实现要求**：
1. **只开 RXNE 中断，不开错误中断（`UART_IT_ERR` / `EIE`）** —— 否则 ORE 会持续触发中断，
   而中断里又没法立即恢复（正在写 Flash），会变成中断风暴
2. 进入接收状态前**清一次 ORE/RXNE 残留**（`uartFlushRx` 已在做，但必须删掉它末尾
   「关中断源」的三行，见 0.6.5）

### 0.6.5 三处现有代码必须一起改（否则打架）

| # | 位置 | 现状 | 必须改成 |
|---|---|---|---|
| 1 | `bl_port_stm32f4.cpp` 的 `uartFlushRx()`（L251-268） | 结尾 `__HAL_UART_DISABLE_IT(RXNE/PE/ERR)` —— **会把接收主路径掐断** | 改为「清 ORE/RXNE + 复位环形缓冲 + 复位解析器状态」，**不关中断源** |
| 2 | 宿主 `stm32f4xx_it.c` 的 `USART1_IRQHandler()`（L219） | 只调 `HAL_UART_IRQHandler(&huart1)` | 在 USER CODE 区插入库的中断入口；库消费了就 `return`，不重复调 HAL。契约 **+1 个函数** |
| 3 | `bl_port_stm32f4.cpp` 的 `uartRead()`（L205-234） | 阻塞轮询 `HAL_UART_Receive(..., 1U)` | 改为从环形缓冲取。**签名不变**，协议层不感知轮询/中断之别 |

> `.ioc` 里 `NVIC.USART1_IRQn=true`（已使能）—— **不需要动 CubeMX**，这是好消息。

### 0.6.6 两端一致性：最大风险点在 CRC8 与字节序

C 与 Python/JS 各写一份 CRC8，**一旦变体不同就全盘失败**（表现为"每一帧都校验错"）。
所以开工第一步是**共享测试向量** —— 已在 PC 侧算好，下表的值就是验收标准：

**CRC8 = CRC-8/SMBUS**（poly `0x07`、init `0x00`、**不反射（MSB-first）**、xorout `0x00`）

| 输入 | 字节数 | 期望 CRC8 |
|---|---|---|
| （空） | 0 | `0x00` |
| `01 02 02 00 34 12`（本文示例帧载荷） | 6 | **`0x12`** |
| `00` | 1 | `0x00` |
| `A5 03` | 2 | `0x50` |
| `00..FF`（0 到 255 全部字节） | 256 | `0x14` |
| `"123456789"` | 9 | `0xF4` |

**CRC32 = ISO-HDLC**（poly `0x04C11DB7`、init `0xFFFFFFFF`、**反射（LSB-first，用反向多项式
`0xEDB88320`）**、xorout `0xFFFFFFFF`）

| 输入 | 期望 CRC32 |
|---|---|
| `"123456789"` | **`0xCBF43926`**（= `bl.cpp` 里已有的 `Crc32::kCheck`，已交叉验过一致） |
| （空） | `0x00000000` |
| `01 02 03` | `0x55BC801D` |

示例帧的完整字节（可直接当解析器单测输入）：

```
A5 01 02 02 00 34 12 12 03
│  │  │  └─len=2─┘ └payload┘ │  └尾
│  │  └ CMD=START            └ CRC8=0x12
│  └ ID=0x01
└ 帧头
```

> ⚠️ **最容易写错的一点：两个 CRC 的位序方向相反。**
> CRC8 是 MSB-first（`c <<= 1`），CRC32 是 LSB-first（`c >>= 1`）。放在同一个文件里很容易
> 顺手写成一个方向。上面 `0x12` 与 `0xCBF43926` 这两个值就是用来抓这个错的 —— 若代码
> 给出 `0x09`（反射版 CRC8）或别的值，就是方向写反了。

同一组向量写进 C 的单元测试与 Python/JS 的单元测试，**两端都过才算对**。
这一步不需要板子 —— 正好利用"协议层不依赖硬件"这个分层，在 PC 上把编解码彻底验完。

### 0.6.7 从机在 RECEIVING 的空闲超时：**30 秒**（已定案）

主机崩溃 / 线缆被拔 → 从机擦除完、回了 READY，然后**永远等下去**。

**定案：加 30 秒空闲超时** —— 30 秒内没收到任何**有效帧**（ID 匹配 + CRC8 通过）就
复位状态机回 `IDLE`。成本几行，换来"状态机能回到干净起点"这个好性质。

两点实现细节：
- 计的是「**有效帧**」而不是「任意字节」—— 总线上别人的帧、噪声都不该帮它续命
- 计时用 `tickMs()`（SysTick）。写 Flash 期间时基会停摆几毫秒，对 30 秒这种粗超时
  无影响

### 0.6.8 块大小与载体上限（提醒）

载体 `DataLen ≤ 1024`，DATA 帧头部 14 字节 → **固件数据最大 1010 字节**。
当前 512 安全；将来若要改大，**上限 1010**，超过就要先抬载体上限。

### 0.6.9 传输期间必须关日志

日志与协议**共用同一个 USART1**。传输期间日志会 ①混进主机的 RX 流 ②抢 TX 带宽
（一帧日志几十字节 ≈ 几毫秒）。→ 进入 IAP 会话后关日志，结束或出错时再开。

---

### 0.6.10 ★ 一次失败的升级会**破坏原有的可用 APP**（运维语义，务必知情）

`START` 一执行就擦除 APP 区 —— **原固件在这一刻就没了**。所以：

- 传输中途失败/放弃 → APP 区是"数据已写但不可启动"（SP/PC 仍是 `0xFF`）
  → 上电停 IAP，**只能重新升级，无法回退到旧固件**
- 这与现有 YMODEM 行为一致（也是先擦后写），但新协议取消了逐块确认，**失败的窗口更长**
- 唯一的安全网是**提交机制本身**：不成功提交就不写 SP/PC，所以设备一定会回到
  "可重刷"状态，**不会变砖**

> 若要"升级失败还能回退"，需要双分区（A/B）—— 本芯片 512KB 装不下（见历史调研）。
> 当前明确不做。用户已知情并接受。

### 0.6.11 主机侧（上位机）的四个细则

| # | 事项 | 要求 |
|---|---|---|
| 1 | 应答超时必须是**帧间计时** | 每次重发都重新起算；不能累积计时（否则重传一多就误判超时） |
| 2 | 超时值要覆盖从机最慢工作 | `DATA` 应答 ≥ 200 ms（从机写 512B 约 2 ms）；`START` ≥ 8 s（擦除约 3.75 s，最坏翻倍）；`END` ≥ 3 s（回读校验毫秒级，留余量） |
| 3 | USB 串口 latency timer | FTDI 默认 16 ms 会放大每个往返（200KB 从 20.6 s 涨到 26.2 s）。CH340 通常 1 ms。网页端要保持紧凑读循环 |
| 4 | 发送缓冲 | 单帧最大 532 B；主机侧按此预分配，别每帧动态分配 |

### 0.6.12 从机中断的两个细节

1. **USART1 中断优先级**：不低于 SysTick（否则接收会被时基/其他中断挤掉；115200 下
   只有一个字节时间 86.8 µs 的余量，够但别拖）
2. **ISR 只做「读 DR → 压入环形缓冲」**，绝不写 Flash、不解析、不发应答 ——
   写 Flash 期间 Flash 总线停摆（RM0090），ISR 自身取指都做不了

## 二、调研：业界四条路线

| 路线 | 代表 | 形态 | 活跃度 | 许可 | 适合我们吗 |
|---|---|---|---|---|---|
| **A. esptool 协议** | ESP8266/ESP32 ROM bootloader | SLIP 成帧 + 8 字节固定头 + 命令码 | 几十亿设备在跑，仍在维护 | 代码 **GPLv2**（协议文档公开） | ★ 形态最贴合我们 |
| **B. mcumgr / SMP** | Zephyr、Mynewt | 分片帧 + Base64 + 7 字节头 + **CBOR** 载荷 | 活跃，Apache 项目 | **Apache-2.0** | 太重（Base64 膨胀 33% + CBOR 编解码） |
| **C. XCP** | OpenBLT | ASAM 标准，命令组（CONNECT/PROGRAM/…） | 汽车级，1000 万台量产 | 规范 ASAM 收费；OpenBLT 实现 **GPLv3** | 能力远超所需（标定/seed-key/多传输层） |
| **D. ST AN3155** | ST 内置 ROM bootloader | 单字节命令 + 定长数据 | 官方但功能固定 | ST 条款（限 ST 芯片） | 太简陋，无成帧、无分块协商 |

### 成帧层的选择：COBS vs SLIP（已废弃，见 §0）

两者都是"用一个定界符把字节流切成帧"，但差别明显：

| | SLIP（RFC 1055） | **COBS** |
|---|---|---|
| 定界符 | `0xC0`，用 `0xDB` 转义 | **`0x00`**（payload 里保证不出现） |
| 最大开销 | **最坏 100%**（payload 全是 `0xC0`/`0xDB` 时翻倍） | **≤ 0.4%**（每 254 字节 1 字节） |
| 1024 字节的实际开销 | 平均 ~8 字节 | **固定 5 字节** + 1 定界符 |
| 解码歧义 | 有（需状态机识别转义序列） | **无**（首字节就是段长） |
| 丢字节后重同步 | 在下一个 `0xC0` 恢复 | 在下一个 `0x00` 恢复 |
| 实现量 | ~40 行 | ~30 行 |

**（历史结论，已废弃）用 COBS。** 开销有界、无歧义、重同步快。它有成熟的参考实现（cobs.c，BSD-3-Clause），算法本身是公开论文，自己写也就 30 行。

### 为什么最终选 A（esptool 形态）〔历史记录〕

1. **形态正好是我们的需求**：`SYNC`（握手）/ `FLASH_BEGIN`（宣告总长 + 擦除）/ `FLASH_DATA`（带偏移的数据块）/ `FLASH_END`（收尾 + 校验）。一一对应。
2. **协议文档公开且详尽**（Espressif 官方文档站），可以按文档自己实现，不碰 GPL 代码。
3. **是最普及的形态**，它的坑早被几十亿台设备踩过。
4. 比 B 轻（不要 Base64/CBOR），比 C 简单（不要标定/seed-key），比 D 完整（有握手、有协商、有错误码）。

> **许可说明**：esptool 的**代码**是 GPLv2，不能抄；但**协议本身是公开规范**，按文档自行实现不受版权约束 —— 这与本项目一贯做法（借鉴架构、自己写代码）一致。

## 三、推荐方案

### 3.1 整体分层

```
┌─────────────────────────────────────────┐
│ 命令层    SYNC / START / DATA / END     │  ← 我们写的，约 80 行
├─────────────────────────────────────────┤
│ 成帧层    COBS：帧定界 + 0x00 消除       │  ← 约 30 行（算法公开）
├─────────────────────────────────────────┤
│ 链路层    CRC16 帧校验                   │  ← 复用现有 Crc16
├─────────────────────────────────────────┤
│ 移植层    uartRead / uartWrite           │  ← 已有，不动
└─────────────────────────────────────────┘
```

**与 YMODEM 最大的结构差异**：没有"协商 / 等 ACK / 超时重传 / 结束序列"这套状态机。数据是**单向流**，出错靠回执纠正，最终靠整片校验兜底。

### 3.2 帧格式

```
COBS 编码后 ──────────────────────────────────────────────────────
  0x00 │ <frame> │ 0x00          ← 定界符；payload 内保证无 0x00
       └─────────┘
              │
解出后的 frame ────────────────────────────────────────────────────
  ┌──────┬─────────┬──────────────┬────────┐
  │ type │ len     │ payload      │ crc16  │
  │ 1 B  │ 2 B(LE) │ len 字节     │ 2 B    │
  └──────┴─────────┴──────────────┴────────┘
  crc16 覆盖 [type..payload 末字节]
```

一帧 1024 字节数据 → 线上 1024 + 4（头尾）+ 5（COBS）+ 1（定界）= **1034 字节**。
对比 YMODEM：1024 包 = 3 + 1024 + 2 = 1029 字节**再加一个 ACK 往返**。

### 3.3 命令集（只有 5 个）

| type | 名称 | 方向 | payload | 板子动作 |
|---|---|---|---|---|
| `0x01` | **SYNC** | 主机→板 | 无 | 回 `ACK` + 芯片信息（Flash 容量、APP 区大小、协议版本） |
| `0x02` | **START** | 主机→板 | `totalLen:4` | 校验 `totalLen ≤ APP 区` → **擦除** → 回 `ACK`（或 `NAK`+原因） |
| `0x03` | **DATA** | 主机→板 | `offset:4` + 数据（≤1024） | 校验 `offset == 已写位置` → 写 Flash。**正常不回话** |
| `0x04` | **END** | 主机→板 | 无 | 回读 `[8, totalLen)` 重算 CRC32 → 提交（写 SP/PC）→ 回结果 |
| `0x10` | **ACK** | 板→主机 | 附加信息（视命令而定） | — |
| `0x11` | **NAK** | 板→主机 | `expectOffset:4` + `reason:1` | — |

**为什么 `DATA` 不要求逐帧应答**：帧级已由 CRC16 保证"这一帧没坏"，整片已由回读 CRC32 保证"全部写对"。逐帧应答只是把这两道检查重复一遍，却要为每个 1KB 付一次往返延迟。

**错误恢复靠 NAK 的 `expectOffset`**：板子发现坏帧或偏移不匹配，回 `NAK(expectOffset)`，主机**从这个偏移继续发** —— 天然实现了断点重传，粒度比 YMODEM 的"重传单包"更合理。

### 3.4 完整时序

```
主机                                板子(Bootloader)
 │                                    │
 ├── SYNC ──────────────────────────► │  握手，取回容量/版本
 │ ◄──────────────────── ACK + 信息 ─┤
 ├── START(totalLen) ───────────────► │  校验 + 擦除（数秒）
 │ ◄───────────────────────── ACK ───┤
 ├── DATA(offset=0, 1024B) ─────────► │
 ├── DATA(offset=1024, 1024B) ──────► │  不逐帧应答
 ├── ...                              │
 ├── DATA(offset=N, 末块) ──────────► │
 ├── END ───────────────────────────► │  回读校验 [8,totalLen) 的 CRC32
 │                                    │  通过 → 写 SP/PC（提交）→ 跳 APP
 │ ◄──────────────── ACK / NAK ──────┤
```

## 四、从成熟方案借来的、我们原本没想到的点

这些是"从零手搓一定漏掉、而业界早就解决过"的东西：

| # | 成熟方案的做法 | 我们的现状 | 要不要吸收 |
|---|---|---|---|
| 1 | **esptool 的 SYNC 用 `0x55` 序列探测/校准波特率** | 硬编码 115200，时钟配错就满屏乱码（本项目实测过 HSE 起不来） | ★ 吸收：握手阶段用固定 pattern 让板子估算波特率偏差 |
| 2 | **esptool 的 `FLASH_BEGIN` 带 `block_size`** | 固定 1024 | 吸收：让板子回"我能收多大块"，主机据此调整 |
| 3 | **esptool 有 20+ 个错误码**（无效参数 / 校验错 / Flash 写错 / 读错 / 长度错…） | 只有 `Status` 枚举，看不出"为什么失败" | ★ 吸收：`NAK.reason` 给出具体原因 |
| 4 | **esptool 的 `FLASH_DEFL_*`：传输前 deflate 压缩** | 无 | 评估：固件重复字节多，通常能压 30-50%，**传输时间直接减半**。代价是板子需要 inflate（约 2-3 KB ROM）—— 对 16 KB 区偏贵，**建议先不做** |
| 5 | **ESP32 的 `SPI_FLASH_MD5` 命令**：读回 Flash 的 MD5 校验 | 已有回读 CRC32（等价思路） | 已具备 |
| 6 | **esptool 的 `CHANGE_BAUDRATE`**：握手低速、传输切高速 | 固定 115200 | 评估：收发要改 DMA 才能吃下高波特率，**本期不做**，但协议留出扩展位 |
| 7 | **mcumgr 的分片帧：总长前置 + 仅末帧带 CRC** | 每帧都带 CRC16 | 保持我们的做法（每帧带校验更适合流式写 Flash） |
| 8 | **COBS 的"丢字节后在下一个定界符重新对齐"** | YMODEM 靠定长 + 超时才能发现错位 | ★ 天然获得 |

**建议本期吸收 #1 #2 #3 #8，评估后暂缓 #4 #6。**
