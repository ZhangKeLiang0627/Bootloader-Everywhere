## 0. 现行设计（已定稿部分）

### 0.1 载体帧（全部命令共用同一种帧）

```
[0xA5] [ID] [CMD] [DataLen:2 LE] [Data ≤1024] [CRC8] [0x03]
  1B    1B   1B   └── 小端 ──┘   └── N ──┘     1B     1B       共 8 + N 字节
```

| 字段 | 规则 |
|---|---|
| `0xA5` | 帧头（兼作波特率探测图案：连发 `0xA5`） |
| `ID` | **从机地址**；`0x00` = 广播（从机收到广播**不回话**）。将来地址存一个 Flash 扇区 |
| `CMD` | **bit7 = 方向位**（0 = 主→从；1 = 从→主）；bit0-6 = 命令码（128 个） |
| `DataLen` | 小端，**≤1024**；`= 0` 合法（无数据命令）；**>1024 立刻丢弃并回错**（不能等收完） |
| `CRC8` | 变体统一为 **CRC-8/SMBUS**（poly 0x07 / init 0x00 / 无反射 / xorout 0x00）；覆盖 `[ID .. Data 末尾]`，**不含 `0xA5` 与 `0x03`** |
| `0x03` | 帧尾。不是冗余：它与 CRC8 一起把「丢字节后重新对齐的误接受率」压到 1/65536 |

**应答帧与请求帧格式相同**，只是 `CMD` 的 bit7 置 1，且**总长 ≤ 32 字节**（数据区 ≤25）。

### 0.2 从机的行为约束

- **从机只有被动应答**：收到询问才回，**不主动发任何帧** → 主机在发数据流时无需监听 RX
- 因此**进度与错误检测必须靠主机 POLL**：`POLL → 应答 [状态:1][已写入偏移:4][期望偏移:4]`
- 波特率**定死**（不做握手协商），但值可以选高一些（见 0.4）

### 0.3 传输层：中断 + DMA（不是可选项）

**真因**：STM32F4 在写/擦 Flash 期间**总线停摆**（RM0090：*code or data fetches
cannot be performed while a write/erase operation is ongoing*）。我们的代码与向量表
都在 Flash 里 → **ISR 自身取指也被 stall**，所以「只开中断」救不了；只有 **DMA** 能
（`USART->DR → SRAM` 走 bus matrix，不碰 Flash 阵列）。

| 波特率 | 字节间隔 | 中断收余量 | 结论 |
|---|---|---|---|
| 115200 | 86.8 µs | 5.4x | 可行 |
| 460800 | 21.7 µs | 0.3x | 不安全 |
| 921600 | 10.9 µs | — | 必然丢 |

形态：**环形 DMA（2 × 1024 B 双缓冲）** + 半传输/传输完成中断 + **流式解析状态机**
（正常时「半区 = 一帧」）。不用 HAL 的 `ReceiveToIdle`（连续流里没有 IDLE），
也不用「精确长度 DMA」（重装间隙会丢字节）。

> 注：**YMODEM 今天没暴露这个问题，是因为它是停等协议**——从机在等 ACK 期间写 Flash，
> 那段时间线上无字节。所以这是**取消逐块 ACK 之后才引入的前置条件**，不是修 bug。

### 0.4 波特率：最大的收益点在这

Flash 写吞吐上限约 **244 KB/s**（16 µs/字 × 256 字/KB），而 115200 只有 11.5 KB/s
—— **21 倍余量被浪费**。传 200 KB 固件：

| 波特率 | 200 KB 耗时 |
|---|---|
| 115200 | 17.4 s |
| 460800 | 4.3 s |
| **921600** | **2.2 s** |

84 MHz PCLK2 下：921600 分频误差 +0.02%，2 Mbps 正好整除（0%）。

### 0.5 待定：DATA 结构

`SYNC` / `START` / `DATA` / `END` / `POLL` 各自的载荷字段、错误码表、两端逐帧时序、
断点续传边界条件 —— 下一轮讨论，本文暂缺。

## 二、调研：业界四条路线

| 路线 | 代表 | 形态 | 活跃度 | 许可 | 适合我们吗 |
|---|---|---|---|---|---|
| **A. esptool 协议** | ESP8266/ESP32 ROM bootloader | SLIP 成帧 + 8 字节固定头 + 命令码 | 几十亿设备在跑，仍在维护 | 代码 **GPLv2**（协议文档公开） | ★ 形态最贴合我们 |
| **B. mcumgr / SMP** | Zephyr、Mynewt | 分片帧 + Base64 + 7 字节头 + **CBOR** 载荷 | 活跃，Apache 项目 | **Apache-2.0** | 太重（Base64 膨胀 33% + CBOR 编解码） |
| **C. XCP** | OpenBLT | ASAM 标准，命令组（CONNECT/PROGRAM/…） | 汽车级，1000 万台量产 | 规范 ASAM 收费；OpenBLT 实现 **GPLv3** | 能力远超所需（标定/seed-key/多传输层） |
| **D. ST AN3155** | ST 内置 ROM bootloader | 单字节命令 + 定长数据 | 官方但功能固定 | ST 条款（限 ST 芯片） | 太简陋，无成帧、无分块协商 |

### 成帧层的选择：COBS vs SLIP（已废弃，见 §0）

两者都是"用一个定界符把字节流切成帧"，但差别明显：

| | SLIP（RFC 1055） | **COBS** |
|---|---|---|
| 定界符 | `0xC0`，用 `0xDB` 转义 | **`0x00`**（payload 里保证不出现） |
| 最大开销 | **最坏 100%**（payload 全是 `0xC0`/`0xDB` 时翻倍） | **≤ 0.4%**（每 254 字节 1 字节） |
| 1024 字节的实际开销 | 平均 ~8 字节 | **固定 5 字节** + 1 定界符 |
| 解码歧义 | 有（需状态机识别转义序列） | **无**（首字节就是段长） |
| 丢字节后重同步 | 在下一个 `0xC0` 恢复 | 在下一个 `0x00` 恢复 |
| 实现量 | ~40 行 | ~30 行 |

**（历史结论，已废弃）用 COBS。** 开销有界、无歧义、重同步快。它有成熟的参考实现（cobs.c，BSD-3-Clause），算法本身是公开论文，自己写也就 30 行。

### 为什么最终选 A（esptool 形态）〔历史记录〕

1. **形态正好是我们的需求**：`SYNC`（握手）/ `FLASH_BEGIN`（宣告总长 + 擦除）/ `FLASH_DATA`（带偏移的数据块）/ `FLASH_END`（收尾 + 校验）。一一对应。
2. **协议文档公开且详尽**（Espressif 官方文档站），可以按文档自己实现，不碰 GPL 代码。
3. **是最普及的形态**，它的坑早被几十亿台设备踩过。
4. 比 B 轻（不要 Base64/CBOR），比 C 简单（不要标定/seed-key），比 D 完整（有握手、有协商、有错误码）。

> **许可说明**：esptool 的**代码**是 GPLv2，不能抄；但**协议本身是公开规范**，按文档自行实现不受版权约束 —— 这与本项目一贯做法（借鉴架构、自己写代码）一致。

## 三、推荐方案

### 3.1 整体分层

```
┌─────────────────────────────────────────┐
│ 命令层    SYNC / START / DATA / END     │  ← 我们写的，约 80 行
├─────────────────────────────────────────┤
│ 成帧层    COBS：帧定界 + 0x00 消除       │  ← 约 30 行（算法公开）
├─────────────────────────────────────────┤
│ 链路层    CRC16 帧校验                   │  ← 复用现有 Crc16
├─────────────────────────────────────────┤
│ 移植层    uartRead / uartWrite           │  ← 已有，不动
└─────────────────────────────────────────┘
```

**与 YMODEM 最大的结构差异**：没有"协商 / 等 ACK / 超时重传 / 结束序列"这套状态机。数据是**单向流**，出错靠回执纠正，最终靠整片校验兜底。

### 3.2 帧格式

```
COBS 编码后 ──────────────────────────────────────────────────────
  0x00 │ <frame> │ 0x00          ← 定界符；payload 内保证无 0x00
       └─────────┘
              │
解出后的 frame ────────────────────────────────────────────────────
  ┌──────┬─────────┬──────────────┬────────┐
  │ type │ len     │ payload      │ crc16  │
  │ 1 B  │ 2 B(LE) │ len 字节     │ 2 B    │
  └──────┴─────────┴──────────────┴────────┘
  crc16 覆盖 [type..payload 末字节]
```

一帧 1024 字节数据 → 线上 1024 + 4（头尾）+ 5（COBS）+ 1（定界）= **1034 字节**。
对比 YMODEM：1024 包 = 3 + 1024 + 2 = 1029 字节**再加一个 ACK 往返**。

### 3.3 命令集（只有 5 个）

| type | 名称 | 方向 | payload | 板子动作 |
|---|---|---|---|---|
| `0x01` | **SYNC** | 主机→板 | 无 | 回 `ACK` + 芯片信息（Flash 容量、APP 区大小、协议版本） |
| `0x02` | **START** | 主机→板 | `totalLen:4` | 校验 `totalLen ≤ APP 区` → **擦除** → 回 `ACK`（或 `NAK`+原因） |
| `0x03` | **DATA** | 主机→板 | `offset:4` + 数据（≤1024） | 校验 `offset == 已写位置` → 写 Flash。**正常不回话** |
| `0x04` | **END** | 主机→板 | 无 | 回读 `[8, totalLen)` 重算 CRC32 → 提交（写 SP/PC）→ 回结果 |
| `0x10` | **ACK** | 板→主机 | 附加信息（视命令而定） | — |
| `0x11` | **NAK** | 板→主机 | `expectOffset:4` + `reason:1` | — |

**为什么 `DATA` 不要求逐帧应答**：帧级已由 CRC16 保证"这一帧没坏"，整片已由回读 CRC32 保证"全部写对"。逐帧应答只是把这两道检查重复一遍，却要为每个 1KB 付一次往返延迟。

**错误恢复靠 NAK 的 `expectOffset`**：板子发现坏帧或偏移不匹配，回 `NAK(expectOffset)`，主机**从这个偏移继续发** —— 天然实现了断点重传，粒度比 YMODEM 的"重传单包"更合理。

### 3.4 完整时序

```
主机                                板子(Bootloader)
 │                                    │
 ├── SYNC ──────────────────────────► │  握手，取回容量/版本
 │ ◄──────────────────── ACK + 信息 ─┤
 ├── START(totalLen) ───────────────► │  校验 + 擦除（数秒）
 │ ◄───────────────────────── ACK ───┤
 ├── DATA(offset=0, 1024B) ─────────► │
 ├── DATA(offset=1024, 1024B) ──────► │  不逐帧应答
 ├── ...                              │
 ├── DATA(offset=N, 末块) ──────────► │
 ├── END ───────────────────────────► │  回读校验 [8,totalLen) 的 CRC32
 │                                    │  通过 → 写 SP/PC（提交）→ 跳 APP
 │ ◄──────────────── ACK / NAK ──────┤
```

## 四、从成熟方案借来的、我们原本没想到的点

这些是"从零手搓一定漏掉、而业界早就解决过"的东西：

| # | 成熟方案的做法 | 我们的现状 | 要不要吸收 |
|---|---|---|---|
| 1 | **esptool 的 SYNC 用 `0x55` 序列探测/校准波特率** | 硬编码 115200，时钟配错就满屏乱码（本项目实测过 HSE 起不来） | ★ 吸收：握手阶段用固定 pattern 让板子估算波特率偏差 |
| 2 | **esptool 的 `FLASH_BEGIN` 带 `block_size`** | 固定 1024 | 吸收：让板子回"我能收多大块"，主机据此调整 |
| 3 | **esptool 有 20+ 个错误码**（无效参数 / 校验错 / Flash 写错 / 读错 / 长度错…） | 只有 `Status` 枚举，看不出"为什么失败" | ★ 吸收：`NAK.reason` 给出具体原因 |
| 4 | **esptool 的 `FLASH_DEFL_*`：传输前 deflate 压缩** | 无 | 评估：固件重复字节多，通常能压 30-50%，**传输时间直接减半**。代价是板子需要 inflate（约 2-3 KB ROM）—— 对 16 KB 区偏贵，**建议先不做** |
| 5 | **ESP32 的 `SPI_FLASH_MD5` 命令**：读回 Flash 的 MD5 校验 | 已有回读 CRC32（等价思路） | 已具备 |
| 6 | **esptool 的 `CHANGE_BAUDRATE`**：握手低速、传输切高速 | 固定 115200 | 评估：收发要改 DMA 才能吃下高波特率，**本期不做**，但协议留出扩展位 |
| 7 | **mcumgr 的分片帧：总长前置 + 仅末帧带 CRC** | 每帧都带 CRC16 | 保持我们的做法（每帧带校验更适合流式写 Flash） |
| 8 | **COBS 的"丢字节后在下一个定界符重新对齐"** | YMODEM 靠定长 + 超时才能发现错位 | ★ 天然获得 |

**建议本期吸收 #1 #2 #3 #8，评估后暂缓 #4 #6。**

## 五、与现有机制的衔接（不变的部分）

这个方案**只替换传输层**，底下的安全设计一个字不动：

| 现有机制 | 变化 |
|---|---|
| **向量表最后写**（提交 = 写 SP/PC） | 不变。`END` 命令触发的就是这套 |
| **回读 CRC32 校验**（提交前读回 `[8,size)` 重算） | 不变，是 `END` 的核心动作 |
| **分区检查 / 向量表合法性（`vectorsSane`）** | 不变 |
| **软件复位唤回 + 15s 窗口** | 不变（`SYNC` 之前板子已在窗口里等） |
| **硬件按钮 / PC13 指示灯** | 不变 |

**代码层面几乎零改动**，因为解耦点早就存在：

```cpp
class Session final : public YmodemSink { ... };   // bl.cpp:310
```

`Session` 只依赖 `onFileStart / onFileData / onFileEnd` 三个回调。新协议只要也实现这三个回调，**`bl.cpp` 一个字都不用改**。
